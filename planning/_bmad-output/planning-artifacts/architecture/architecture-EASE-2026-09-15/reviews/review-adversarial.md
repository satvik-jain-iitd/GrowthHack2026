# Spine Review — Adversarial Divergence Attack

## Verdict
The spine has the right layer split and deterministic-validation stance, but it leaves several shared contracts and mutation-order rules underspecified enough that parallel hackathon teams can each comply with every AD and still ship an incompatible demo.

## Hole 1 — Bridge selector ownership and freshness — critical
- **Unit A:** Frontend/UI dev building `SpotlightRing` and `ProgressPanel` in `prototype/ease-chrome/components/`, consuming a `lib/bridge/selectors.ts` map like `{ step: 3, target: "[data-ease-target='table-max-party']" }` to position exactly one ring per Step.
- **Unit B:** Host App Skin dev extending `prototype/walkthrough-assistant/index.html` and `js/` to add the Step 3 table editor, then later renaming or nesting the max-party-size field markup while preserving the visual UI and host-app behavior.
- **Both obey:** AD-1 says contact is documented DOM selectors plus pub/sub, and neither layer imports the other. AD-2 says the Host App Skin retains and extends the vanilla prototype. EXPERIENCE says one active Spotlight Ring per Step and that the ring follows the host control. Nothing says which unit owns selector registration, whether selectors are generated from host markup, or how stale selectors fail.
- **Yet diverge because:** the Chrome Layer can keep a valid-looking selector map that points at no element or the wrong duplicated element after the Host App Skin change. The UI dev still uses the Bridge, and the host dev still exposes DOM controls, but Step 3 now has zero rings, two rings, or a ring on the wrong field during the live demo. The failure is not caught until integration because selector freshness is not a typed or testable contract.
- **Close it with:** **Tighten AD-1 — Bridge selectors are owned by a single versioned `BridgeContract` generated or declared in `lib/bridge/bridge-contract.ts`, and every Host App Skin target used by Steps 1–6 must declare exactly one matching `data-ease-target` from that contract. Startup must run a contract check that fails loudly before a Journey starts if any required selector resolves to zero or more than one element. No component may define ad hoc selectors inline.**

## Hole 2 — Event bus vocabulary split — critical
- **Unit A:** Host App Skin dev emitting raw events from vanilla JS: `floorplan:saved`, `table:changed`, `shift:updated`, each with payloads shaped around host internals such as `{ planName, selectedShiftId }`.
- **Unit B:** Validation/metrics dev subscribing in the EASE Chrome Layer to events they inferred from PRD terminology: `journey.step.completed`, `validation.failed`, `shift.floorPlanSelected`, with payloads like `{ journey_id, step, entityId }`.
- **Both obey:** AD-1 permits a pub/sub event bus and says the Host App Skin emits raw DOM/state events while EASE subscribes. AD-6 defines TelemetryEvent names, not bridge bus event names. Consistency Conventions say to use PRD glossary terms in identifiers, but do not define the bus enum, direction, or payload envelope.
- **Yet diverge because:** both devs create Bridge-compliant events but no listener receives the producer's event names. Validation never sees Step 5 saved or Step 6 activated, or the telemetry layer maps bridge events differently than the validation layer. A successful host interaction can produce zero validation, zero telemetry, or the wrong Step transition while every unit still used the Bridge.
- **Close it with:** **Tighten AD-1 — the Bridge event bus has a closed, versioned enum and payload schema in one shared contract: `host.floorPlan.changed`, `host.floorPlan.saved`, `host.shift.floorPlanSelected`, `host.shift.availabilityVisible`, `host.navigation.changed`, and `ease.journey.commanded` only for MVP. Host App Skin may emit only `host.*`; EASE may emit only `ease.*`; unknown events are rejected in development and logged as contract violations.**

## Hole 3 — Double or missing TelemetryEvent emission — high
- **Unit A:** UI dev instruments `SpotlightRing`/`ProgressPanel` to satisfy FR-9 by writing `step_viewed`, `help_requested`, and `step_completed` when the current Step visually changes or a user clicks a highlighted control.
- **Unit B:** Backend/validation dev instruments the Validation Engine and Telemetry Emitter to satisfy AD-4/AD-6 by writing `validation_failed`, `step_completed`, and `journey_completed` after deterministic validation passes.
- **Both obey:** AD-6 says every TelemetryEvent carries the required envelope. FR-9 says the system emits events for the eight occurrence types. AD-4 says validation is deterministic. The Capability Map places FR-9 in `lib/telemetry/` but also names UI components as the sources for FR-3/FR-4; no AD states which component is the sole emitter for each logical occurrence.
- **Yet diverge because:** Step 3 completion can be emitted once by the UI when the owner clicks Save/Next and again by the Validation Engine when required fields pass, producing a Micro-Guide with duplicate Step 3 cards. Or both teams assume the other owns `step_viewed` and no Step 1 view event exists, violating FR-10 ordering. The same Journey run can look complete in SQLite but incomplete or duplicated in JSONL.
- **Close it with:** **New AD — Telemetry emission ownership is centralized: only `lib/telemetry/TelemetryEmitter` writes JSONL, and each event type has exactly one producer. UI components may request `help_requested` and `step_viewed` through typed commands; only the Validation Engine may emit `step_completed`, `validation_failed`, `journey_completed`, and `journey_abandoned` after reconciling Journey state. `TelemetryEmitter` must enforce idempotency on `(journey_id, event_type, step, occurrence_key)`.**

## Hole 4 — LLM-inferred Step versus Validation-owned Step — critical
- **Unit A:** AI intent dev implements AD-3 FR-2 in the LLM Boundary Service: given screen text and host state, it returns `{ currentStep: 4, confidence: 0.82, targetControl: "combination-builder" }` to resume mid-flow.
- **Unit B:** Backend/validation dev implements AD-4 and Consistency Conventions: Journey/Step state is mutated only by the Validation Engine, which sees required table fields still missing and keeps `current_step = 3` in SQLite.
- **Both obey:** AD-3 explicitly assigns screen-state-to-Step inference to the LLM Boundary. AD-4 says completion/validation is deterministic. Consistency Conventions say Journey/Step state is mutated only by the Validation Engine. FR-2 says the system determines the current Step from app state, but not whether the LLM result is authoritative, advisory, or subject to validation reconciliation.
- **Yet diverge because:** Progress Panel and Spotlight Ring can render Step 4 from the LLM response while Validation Message blocks Step 3 from the relational Journey state. Both teams can truthfully say the LLM did inference and the Validation Engine owned mutation. The owner sees current Step mismatch, and telemetry may tag the same user action as Step 3 or Step 4 depending on which module handles it.
- **Close it with:** **Tighten AD-3/AD-4 — LLM Step inference is advisory only. The authoritative `current_step` is computed and persisted by the Validation Engine from a deterministic `JourneySnapshot`; the LLM may propose a Step only as an input to reconciliation. If LLM-proposed Step differs from validation-derived Step, the Validation Engine wins, the UI renders the validation-derived Step, and a non-journey-debug event records the disagreement.**

## Hole 5 — Journey ID split across SQLite and JSONL — critical
- **Unit A:** Metrics/lifecycle dev creates `journey_id = crypto.randomUUID()` in `TelemetryEmitter` when the first `journey_started` event is written to JSONL.
- **Unit B:** Backend/state dev creates `journey_id = crypto.randomUUID()` in SQLite when the Validation Engine inserts the `journeys` row on first successful intent resolution.
- **Both obey:** Consistency Conventions require UUIDv4 for `journey_id`. AD-5 deliberately separates relational Journey/Micro-Guide records from the append-only telemetry log and says they are never joined at the schema level. AD-6 requires `journey_id` in every TelemetryEvent. No AD defines the single issuer for `journey_id` or requires both stores to share a JourneyRun envelope.
- **Yet diverge because:** both stores contain compliant UUIDv4 values that refer to the same human run but are not equal. Micro-Guide generation reads SQLite Journey `A` and JSONL events under Journey `B`, so it finds no events, generates an empty guide, or falls back to a timestamp merge that picks the wrong run. This is invisible in unit tests that validate each store independently.
- **Close it with:** **New AD — `journey_id` is minted exactly once by `JourneyRunFactory` before any store write, carried in a required `JourneyContext` through LLM, validation, telemetry, and guide generation, and never regenerated downstream. SQLite `journeys.id` and every JSONL `TelemetryEvent.journey_id` for a run must be byte-identical; any missing context is a hard error, not auto-creation.**

## Hole 6 — Dual-store partial writes and recovery — high
- **Unit A:** Backend/validation dev persists Step 6 success and Journey completion to SQLite first, then calls `TelemetryEmitter` to append `journey_completed` to JSONL.
- **Unit B:** Metrics/lifecycle dev appends telemetry first and intentionally keeps JSONL out of the relational transaction to obey AD-5's "never written into the relational store's transactional path" rule.
- **Both obey:** AD-5 requires relational state for Journey/Micro-Guide and append-only JSONL for TelemetryEvents, with no schema-level join and no telemetry in the relational transactional path. AD-6 defines the event shape. Nothing defines write ordering, retry behavior, or how the system behaves if SQLite succeeds and JSONL fails, or vice versa.
- **Yet diverge because:** a crash or filesystem lock can leave SQLite saying `journey.status = completed` with no `journey_completed` event, preventing FR-10's guide sequence from matching telemetry. The inverse leaves a `journey_completed` JSONL event for a Journey row that never completed, causing the Micro-Guide Generator to produce a candidate from an invalid run. Both implementations respect the two-store boundary but disagree on durability semantics.
- **Close it with:** **New AD — cross-store writes use a deterministic outbox-style handoff: the Validation Engine commits authoritative Journey state in SQLite and records a pending telemetry intent in a local outbox table; `TelemetryEmitter` drains the outbox to JSONL with retries and marks intents delivered. The Micro-Guide Generator may run only when SQLite says completed and all required telemetry intents for that Journey are delivered.**

## Hole 7 — Micro-Guide merge key and ordering ambiguity — high
- **Unit A:** Guide-generator dev implements AD-5/FR-10 by reading SQLite `journeys`/`micro_guides` and JSONL telemetry, then sorting events by `timestamp` and creating one card per `step_completed` event.
- **Unit B:** Frontend/UI dev implements Spotlight telemetry attributes as `{ control: "maxPartySize", selector: "[data-ease-target='table-max-party']" }` and emits `step_viewed` when the visual ring updates; Validation Engine emits `step_completed` without the highlighted-control attributes because AD-6 requires only `attributes` map, not its contents.
- **Both obey:** AD-5 says the generator reads both stores and merges in application code. AD-6 allows flexible `attributes`. PRD FR-10 requires the guide include Step, highlighted control, and Step 6 catch if triggered, but the spine does not define the merge key between `step_viewed` and `step_completed`, nor the canonical ordering field beyond ISO timestamp.
- **Yet diverge because:** timestamps from UI and server can tie, skew, or arrive out of order; `step_completed` has no control data while `step_viewed` has no completion proof. The generator either creates cards missing highlighted controls, pairs Step 4 completion with the Step 5 spotlight, or sorts rapid events incorrectly. The Micro-Guide can fail FR-10 despite all events being OTel-shaped and all persistence rules followed.
- **Close it with:** **Tighten AD-5/AD-6 — every TelemetryEvent carries a monotonic `sequence_number` assigned by `TelemetryEmitter` per `journey_id`, plus `step_instance_id` for each Step attempt. `step_viewed`, `validation_failed`, and `step_completed` for the same attempt must share `step_instance_id`; Micro-Guide generation merges only on `(journey_id, step, step_instance_id)` and orders by `sequence_number`, never wall-clock timestamp.**

## Hole 8 — Host state snapshot shape mismatch — high
- **Unit A:** Host App Skin dev models the mocked floor plan as browser-local objects: `{ tables: [{ id, label, min, max, kind }], combinations: [{ tableIds, min, max }] }`, exposed in Bridge events as raw host state.
- **Unit B:** Validation Engine dev writes pure functions over a Journey-domain shape: `{ floorPlan: { tables: [{ tableId, tableType, minPartySize, maxPartySize }], combinations: [{ memberTableIds, combinedCapacity }] }, shift: { activeFloorPlanId } }`.
- **Both obey:** AD-4 requires validation as pure functions over Host App Skin / Journey state. AD-1 says the Host App Skin emits raw DOM/state events. Consistency Conventions define only validation failure shape, not the canonical Host-to-Validation snapshot schema. AD-8 says the mocked host app is the system boundary, but not the data contract inside that boundary.
- **Yet diverge because:** validation receives host payloads whose fields are semantically equivalent but named or typed differently. `max` can be a string from an input, `tableIds` can be host DOM IDs while validation expects Journey entity IDs, and `combinedCapacity` can mean `"6-8"` or `{ min: 6, max: 8 }`. Each unit passes its own tests, but Step 3/4 validation falsely fails or falsely passes at integration.
- **Close it with:** **New AD — define a canonical `JourneySnapshot` DTO as the only input to Validation Engine and LLM Step reconciliation. Bridge adapters, not validators, translate raw Host App Skin DOM/state into this DTO with normalized field names, numeric types, stable entity IDs, and explicit nulls for missing fields. Validation functions may not consume raw host events directly.**

## Hole 9 — Async stale responses mutate the live Journey — high
- **Unit A:** AI intent dev makes LLM Step inference asynchronous and returns results whenever the provider responds; the UI applies the latest resolved promise to update current Step and Spotlight target.
- **Unit B:** Frontend/UI and validation devs support rapid owner interactions: the owner completes Step 2 and Step 3 before a slow FR-2 inference request from the Step 2 screen returns, and validation has already persisted `current_step = 4`.
- **Both obey:** AD-3 says the LLM Boundary Service is real-time request/response and stateless. AD-4 says validation mutates Step state deterministically. EXPERIENCE assumes continuous validation with no retry button and says rapid guidance should follow the current control. No AD defines correlation IDs, cancellation, or stale-result rejection for asynchronous LLM/validation results.
- **Yet diverge because:** the late LLM response for an old host snapshot can move the Spotlight/Progress Panel back to Step 2 or emit a stale `step_viewed` event after Step 4 has started. The live demo now flickers backward or produces telemetry order `Step 4 viewed` then `Step 2 viewed`. Both teams followed their boundaries; the missing rule is temporal ownership.
- **Close it with:** **New AD — every async inference/validation request carries `journey_id`, `snapshot_version`, and `requested_at_sequence`. UI may apply a response only if its `snapshot_version` equals the latest version known to the Validation Engine; stale responses are discarded and may not mutate Journey state, Spotlight target, Progress Panel, or telemetry.**

## Hole 10 — Canonical Micro-Guide race in Specialist Review — medium
- **Unit A:** Specialist Review dev implements Approve/Reject buttons by updating the visible `micro_guides.status` row directly: `pending_review -> approved` or `rejected`.
- **Unit B:** Metrics/lifecycle or guide-generator dev allows a re-run of the same Journey after completion and creates another `pending_review` Micro-Guide while a prior pending or approved guide exists, because PRD says single-run generation only and rejects full versioning as out of scope.
- **Both obey:** AD-5 says Micro-Guide records are relational and Specialist Review uses `pending_review -> approved | rejected` only. FR-11 says approving treats a guide as canonical and a prior approved guide remains canonical on rejection. The spine explicitly defers full Studio versioning, but it does not define the relational uniqueness rule for "canonical" or whether multiple pending candidates for the same Journey are allowed in a demo re-run.
- **Yet diverge because:** two `approved` rows can exist for the Build Floor Plans Journey, or a rejected second guide can accidentally clear the first guide's canonical status if the review code treats "latest guide" as canonical. The owner re-run then reflects a different guide depending on query ordering (`ORDER BY created_at DESC` vs `WHERE status='approved' LIMIT 1`).
- **Close it with:** **Tighten AD-5 — for MVP, relational storage enforces at most one `pending_review` candidate and at most one `approved` canonical Micro-Guide per Journey definition. Approve must atomically set the approved guide as canonical and demote any previous approved guide only if replacement is intended; Reject must never mutate the existing canonical guide. All canonical reads must use `is_canonical = true`, not timestamp ordering.**
