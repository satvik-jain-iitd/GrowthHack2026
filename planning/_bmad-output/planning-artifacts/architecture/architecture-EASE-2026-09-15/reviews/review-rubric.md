# Spine Review — Rubric Walker

## Gate verdict
HOLD: the spine has a solid product/architecture core, but it is not yet a good-spine pass because bridge contracts, demo topology, brownfield delta, QA, and security/error envelopes are still loose enough for downstream teams to diverge.

## 1. Divergence coverage — adequate
- **high** finding (`ARCHITECTURE-SPINE.md` §Design Paradigm, AD-1, Structural Seed). The Bridge is named as “documented DOM selectors + pub/sub event bus,” but the spine does not actually define the selector catalog, event names, payload shapes, or ownership/versioning for the Step 1–6 control map. Two teams can independently build Host App Skin anchors and Chrome Layer consumers that both satisfy AD-1 in spirit but fail to interoperate. *Fix:* add a Bridge Contract table with one row per Step/control, required `data-ease-*` selector, emitted event name, payload schema, and owner; make unknown/missing selector behavior fail-closed.
- **medium** finding (`ARCHITECTURE-SPINE.md` AD-6, Capability → Architecture Map). FR-9 maps to a telemetry emitter and event envelope, but not to a lifecycle matrix specifying exactly when `journey_started`, `step_viewed`, `step_completed`, `validation_failed`, `backtracked`, `help_requested`, `journey_abandoned`, and `journey_completed` fire and which component emits them. Telemetry and Micro-Guide teams could diverge while still emitting “OTel-shaped” events. *Fix:* add an event lifecycle/producer matrix and use it as the contract for FR-9/FR-10.

## 2. AD enforceability — adequate
- **medium** finding (`ARCHITECTURE-SPINE.md` AD-7). AD-7’s “anything not on the built list should default to reuse” is directionally right but too broad to fail a PR on; it is closer to a principle than a constraint. It prevents commodity reinvention only when a reviewer can point to a named forbidden build decision. *Fix:* either move the broad sentence to rationale or replace it with reviewable constraints, e.g. “no custom design-system primitives where DLS has an equivalent,” “no bespoke LLM client outside `lib/llm-boundary/`,” and “validation rules must be first-party code in `lib/validation/`.”
- **medium** finding (`ARCHITECTURE-SPINE.md` AD-2 and Structural Seed). AD-2 says the existing prototype is “retained and extended,” while the source tree labels `walkthrough-assistant/` “existing, unchanged,” and the new Chrome app may live in `prototype/ease-chrome/` “or equivalent.” That leaves both modification scope and path ownership non-enforceable. *Fix:* choose the exact Chrome path and say explicitly which brownfield files may change for Host App Skin adaptation.
- **low** finding (`ARCHITECTURE-SPINE.md` AD-6). “OTel-shaped” is mostly enforceable via required fields, but the rule does not name the semantic-convention mapping or namespace for `event_type` values. *Fix:* define the allowed event enum and attribute namespace in the spine or a linked schema file.

## 3. Deferred safety — thin
- **high** finding (`ARCHITECTURE-SPINE.md` Stack and Deferred). The Stack decides/assumes a Node.js Next API route for the LLM Boundary Service, but Deferred reopens “LLM Boundary Service language/runtime.” That can split UI, API, config, and deployment work into incompatible tracks. *Fix:* do not defer the runtime/contract; freeze at least the HTTP/API contract, provider-adapter interface, env var names, and demo runtime now. If language is still negotiable, defer only the implementation language behind that fixed contract.
- **high** finding (`ARCHITECTURE-SPINE.md` Deferred). “Deployment & environments beyond the demo laptop” is deferred, but the spine still needs the demo topology: how a vanilla static Host App Skin and a Next.js Chrome Layer share one browser tab, same-origin/CORS assumptions, ports, startup order, and reset data location. Without this, Host and Chrome units can be built in ways that cannot be presented together. *Fix:* add a local-demo environment decision/runbook: served paths, ports, build/start commands, data files, and reset procedure; keep cloud/CI/CD deferred if desired.

## 4. Tech currency — adequate
- **medium** finding (`ARCHITECTURE-SPINE.md` Stack; `prototype/package.json`). Next.js 16.3.5 is current per npm, but the architecture is not persistent in code: `prototype/package.json` has Next scripts and no `dependencies`, and the stack says Node.js `20+` even though Next 16.3.5 declares `>=20.9.0`. *Fix:* in the chosen Chrome app package, pin/declare `next`, `react`, `react-dom`, and DLS dependencies, and specify Node `>=20.9.0` (or the exact team runtime) in the spine.
- **low** finding (`ARCHITECTURE-SPINE.md` Stack). `@americanexpress/dls-react ^7.15.0` is consistent with the local design-system skill, but the spine does not name the private registry/install source, so an external reviewer cannot independently verify or install it from the public npm registry. *Fix:* cite the local design-system skill/approved Amex registry as the source of truth and carry the dependency into the Chrome package manifest.

## 5. Brownfield ratification — thin
- **high** finding (`ARCHITECTURE-SPINE.md` AD-2, Structural Seed; `prototype/walkthrough-assistant/README.md`; prototype file list). The existing vanilla mock is a working Resy-like substrate, but its documented journeys are Create a Shift, Going Live, and Invite a Team Member; it is not the PRD’s Build Floor Plans Step 1–6 flow. The spine’s “as-is”/“unchanged” wording therefore over-ratifies brownfield reality and under-specifies the required delta. *Fix:* ratify the shell, styling tokens, navigation, walkthrough engine, recorder, and static floor-plan reference as reusable, but explicitly require Host App Skin changes/additions for Floor Plan Settings, table-field editing, combinations, Save, Shift activation, and Shift Availability confirmation.
- **medium** finding (`ARCHITECTURE-SPINE.md` AD-2; `prototype/package.json`). The spine correctly rejects the empty root Next.js stub as usable implementation, but it does not say whether to delete, ignore, or supersede its scripts/package boundary. *Fix:* state the package ownership model: either convert `prototype/package.json` into the real Chrome app manifest or create `prototype/ease-chrome/package.json` and mark root scripts non-authoritative.

## 6. Spec coverage — adequate
- **low** finding (Capability → Architecture Map). No FR is completely homeless: FR-1 through FR-11 and UJ-1/UJ-2 all appear in the map. However, FR-2’s mid-journey resume consequence is mapped only to `lib/llm-boundary/`; the architecture does not name the durable/derived state source that lets the LLM boundary infer “next incomplete Step” after close/reopen. *Fix:* add `JourneyRun`/local state ownership and specify that FR-2 consumes a deterministic Host/Journey state snapshot, not model memory.
- **low** finding (Capability → Architecture Map, FR-11). UJ-2/FR-11 covers approve/reject state, but the map does not name the retrieval rule that makes an approved guide canonical on a re-run. *Fix:* add a `canonical_micro_guide` selection rule or query contract to the Micro-Guide state section.

## 7. Inherited-invariant consistency — adequate
- **high** finding (`ARCHITECTURE-SPINE.md` Inherited Invariants). The table binds “Web-only, single surface, Steps 1–6” and “No real external system integration” to AD-9, but no AD-9 exists. That weakens traceability for two inherited invariants reviewers must be able to enforce. *Fix:* change the bindings to Scope/AD-8/Deferred as appropriate, or add an explicit AD-9 that owns web-only/single-surface/demo boundary.
- **low** finding (`ARCHITECTURE-SPINE.md` Stack). The inherited supported-model invariant lists Azure GPT 5.2, LLAMA 3.2/3.3, and Gemini-3.1-flash-lite; the Stack narrows implementation to Azure default plus LLAMA fallback. This does not contradict the invariant, but it should be stated as a deliberate subset to avoid later claims that Gemini support is required. *Fix:* add “Gemini is supported by the event but not targeted for this MVP unless Azure/LLAMA access fails.”

## 8. Dimension completeness — thin
- **high** finding (whole spine). Testing/QA strategy is effectively silent. The spine says validation functions are testable, but does not decide unit/contract/e2e coverage for deterministic validation, Bridge selectors/events, FR-1 paraphrase/non-match set, telemetry ordering, Micro-Guide fidelity, Specialist Review state transitions, or DLS/WCAG checks. *Fix:* add a QA dimension with required test layers and minimum acceptance tests mapped to FR-1–FR-11.
- **high** finding (`ARCHITECTURE-SPINE.md` Consistency Conventions, Stack, AD-3). Security/privacy is under-specified. Credentials are only said to live in one env-config module; there is no rule for secret storage, redaction/minimization of screen state sent to the LLM, telemetry PII avoidance, local data retention/reset, or outbound allow-listing beyond “no real Resy/Toast/Salesforce/POS.” *Fix:* add a security envelope: env var names/no client exposure, redact/minimize Host App state before LLM calls, no PII in JSONL, local file cleanup/reset, and allowed outbound hosts.
- **medium** finding (whole spine). Error handling/failure modes are mostly absent: LLM unavailable or slow, selector missing, validation exception, SQLite write failure, JSONL append failure, and review transition conflicts are not governed. *Fix:* add fail-closed rules: deterministic demo fallback for FR-1, no step completion on validation errors, visible “not supported/unavailable” messages, telemetry buffering/drop policy, and idempotent approve/reject handling.
- **medium** finding (`ARCHITECTURE-SPINE.md` Deferred). Operations/environment is deferred rather than owned at the MVP altitude. Cloud, CI/CD, and multi-environment promotion can remain out of scope, but the local operational envelope for the demo is load-bearing. *Fix:* add a minimal ops/runbook section covering startup commands, ports, data file paths, seed/reset, model config, and demo-health checks.
