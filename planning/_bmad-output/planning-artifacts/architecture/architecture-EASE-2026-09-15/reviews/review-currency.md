# Spine Review — Technology Currency

## Verdict
Changes required before the Reviewer Gate can pass: the public Next/React claims are current, but the committed Node floor, SQLite access plan, internal DLS installability, and LLM model-default wording need correction or explicit confirmation.

## Verified against live sources
- **Next.js** — claimed `16.3.5 (latest stable, verified 2026-09-15)`; actual npm `latest` is `next@16.3.5` (https://registry.npmjs.org/next/latest). Verdict: version claim verified current. Caveat: the package engine is `node >=20.9.0`, so `Node.js 20+` is not precise enough, and this repo's local Node `v18.20.8` cannot run it.
- **Next.js React compatibility** — the spine says `React 19 (Next.js 16 default)`. `next@16.3.5` peer dependencies allow `react`/`react-dom` `^18.2.0 || 19.0.0-rc-de68d2f4-20241204 || ^19.0.0` (https://registry.npmjs.org/next/latest). Verdict: React 19 is compatible/default, but not strictly required by the package peer range.
- **create-next-app live default** — `create-next-app@16.3.5` is npm `latest` and requires `node >=20.9.0` (https://registry.npmjs.org/create-next-app/latest). Its shipped `dist/index.js` sets `react` and `react-dom` to `19.2.8` in generated app dependencies (https://unpkg.com/create-next-app@16.3.5/dist/index.js). Verdict: the live starter defaults to React 19, but the exact starter default is `19.2.8`, not npm's latest React patch.
- **React** — claimed `19`; actual npm `latest` is `react@19.3.0` (https://registry.npmjs.org/react/latest). Verdict: current major verified.
- **Node.js release schedule** — claimed `20+`; Node schedule shows v20 ended 2026-04-30, v22 is in maintenance through 2027-04-30, and v24 is LTS through 2028-04-30 (https://raw.githubusercontent.com/nodejs/Release/main/schedule.json). Verdict: `20+` satisfies Next's minimum only if `>=20.9.0`, but is stale as a currency recommendation on 2026-09-15.
- **SQLite access options** — `better-sqlite3@13.0.3` is npm `latest` and requires `node >=22` (https://registry.npmjs.org/better-sqlite3/latest); `sqlite3@6.0.1` is npm `latest` and requires `node >=20.17.0` (https://registry.npmjs.org/sqlite3/latest); Node's built-in `node:sqlite` was introduced in `v22.5.0` and is documented in Node v22.19.0 as Stability 1.1 / active development (https://nodejs.org/download/release/v22.19.0/docs/api/sqlite.json). Verdict: current embedded SQLite choices require an explicit driver/runtime decision and do not work on the current dev-machine Node `v18.20.8`.
- **Existing project stub** — local `prototype/package.json` has Next scripts only and no dependencies. Verdict: AD-2's claim that the current root Next scaffold is not a usable dependency-declared app is reality-checked against the repo.

## Findings
- **[high] Runtime floor is stale and locally incompatible** (`ARCHITECTURE-SPINE.md` Stack, Node.js row; LLM Boundary Service runtime row). The stack says `Node.js 20+`, but Next/create-next-app 16.3.5 require `>=20.9.0`; Node v20 is EOL as of 2026-04-30; and this dev machine is actually on `v18.20.8`, which cannot run the chosen starter/framework. *Fix:* pin a non-EOL demo/runtime version, preferably Node 24 LTS (or at minimum Node 22+ if using current SQLite drivers), add an `.nvmrc`/`.node-version`/Volta entry or setup instruction, and update `Node.js 20+` to the exact supported floor.
- **[high] SQLite is named without an installable Node access path** (`ARCHITECTURE-SPINE.md` Stack, Relational store row; Structural Seed `db/schema.sql`). `SQLite (embedded)` is not a Node dependency or API by itself. Current options have different runtime constraints: `better-sqlite3@13.0.3` requires Node `>=22`, `sqlite3@6.0.1` requires Node `>=20.17.0`, and `node:sqlite` exists only from Node `v22.5.0` and is still active-development in v22 docs. None work on the current Node `v18.20.8`. *Fix:* choose and pin the driver now (recommended: align runtime to Node 24 LTS and use either `better-sqlite3` for simple synchronous embedded demo storage, or explicitly choose `node:sqlite` if accepting its stability status), then reflect that dependency in the stack.
- **[medium] DLS version range matches the vendored skill, but installability is a hackathon risk** (`ARCHITECTURE-SPINE.md` Stack, `@americanexpress/dls-react` row; Inherited Invariants DLS v7 row). The local skill supports `@americanexpress/dls-react` 7.x including `^7.15.0`, but the package is internal and cannot be installed from public npm here; registry credentials/access are unverified. React 19 peer compatibility is also not confirmed by the vendored skill. *Fix:* before Build, confirm team access to the internal npm registry and DLS React v7 peer support for React 19, or document a fallback packaging/demo plan that still meets the DLS requirement.
- **[low] LLM Stack row partially hard-codes model selection and omits one supported model** (`ARCHITECTURE-SPINE.md` Stack, LLM Boundary Service row). The inherited invariant lists Azure GPT 5.2, LLAMA 3.2/3.3, and Gemini-3.1-flash-lite, but the Stack row names Azure GPT 5.2 as the default and LLAMA as fallback, omitting Gemini. That can accidentally commit the build to credentials the team may not receive. *Fix:* reword the Stack row to say the provider/model is selected only from event-issued credentials/config among the internal FAQ-supported models, and include Gemini in the listed options rather than committing an architectural default.
