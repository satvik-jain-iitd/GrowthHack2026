Conformance to the AmEx Architecture Portal

Every prescriptive ADR that could apply was checked. Nothing here is a silent departure — where the demo does something different, it says so and names the production path.

Conforms

One App

The ADR prescribes One App for dynamic, high-interaction, multi-step journeys. The Chrome Layer is a One App Single Module. No exemption needed.

Conforms

Design Language System

All Amex-built UI is DLS v7. The non-DLS surface is a simulation fixture representing a partner product, so the ADR's scope does not reach it.

Conforms in pattern

AI / ML

A real-time, request-response GenAI microservice, as the ADR prescribes. The batch, no-code alternative was considered and rejected as a poor fit for an interactive flow.

Conforms in type selection

Database

The ADR asks for the data type to be chosen before the platform: relational for workflow state, append-only log for events. Both followed; the demo platforms are fixtures.

Scoped exception

Observability

There is no deployed environment to observe, so the demo logs locally. Bounded by keeping every event enterprise-compatible in shape — production wiring becomes configuration, not a rewrite.

Not applicable

API & Integration Platforms

Both services are loopback-only processes on one laptop, not exposed or enterprise-consumed APIs. Re-classify before anything is exposed beyond the demo machine.

Not applicable

Event Brokers & Messaging

The bridge event bus is in-browser and the telemetry log is a local file. Neither is the inter-service messaging this ADR governs.

Conforms

Build vs Buy

Below all three formal triggers. Buy the rails — One App, DLS, the model, the datastore. Build the intelligence — the journey model, the validation rules, the telemetry.
